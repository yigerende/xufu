# 浏览器完整账单税费报价同步

2026-10-31 正式第四套流程 `cslive_browser` 的一次失败：16:51:47（Asia/Shanghai）保存报价 PHP 649000 分，16:51:47.811、16:51:49.508 仍收到 checkout.session 更新；16:52:02 返回 `amount_changed`。原单 `submitted=false`，无付款请求实际提交事件、无实收证据，服务费已解冻。没有重放原单或发起真实支付。

原有浏览器税费确认未被第四套删除：第四套新增提交 349f1c3 没有修改浏览器运行时。原条件仅要求填地址后有响应、税费就绪且静默超过 1.5 秒，没有关联请求中的完整账单地址，也没有等待在途账单更新。原金额在报价事件落库；后续金额变化触发防护，不会将失败时的新金额覆盖成已授权报价。因此前端仍显示之前的 PHP 6,490.00。

正式历史日志没有保留各次税费金额及完整请求关联，无法确定最终税额或是哪一次地址更新。离线浏览器测试复现了提前锁定旧价并被 `amount_changed` 拦截的时序。参考用户完整 HAR 的合法税区更新结构，以及旧 HTTP、新 cs-live 的完整账单税区更新流程，修复浏览器观察逻辑：

- 只从原 checkout 的完整 `tax_region` 更新响应取得最终报价。国家、州、邮编、地址和城市必须匹配本单已保存账单；不选择或更换地址以调整税额。
- 完整响应必须有效、税费完成、会话开放；所有已发出的账单更新必须返回，最后有效状态仍来自匹配响应，并达到稳定窗口。旧响应晚到、地址不完整/不匹配、错误/其他 checkout 响应以及超时未稳定均不授权付款。
- 等待响应解析完成后才锁价；用户/服务端授权后的 IP 检查前后，以及实际 confirm 的 IP 检查前后，再次核对报价和在途税费更新。原金额保护与单次提交规则保留。
- 诊断区分初始化、账单更新、准备付款方式、付款确认和只读查询。实际提交前的税费更新归类为报价，不再仅因已经生成报价就显示为结果查询。只使用现有白名单，不保存完整地址、原始响应、卡片或令牌。

修复共用于 `legacy`、`cslive_browser` 的官方 hosted 浏览器付款；原提链、代理/IP规则、随机正式账单、套餐长短链选择、验证/订阅核实/刷新和续费规则不变。

新增离线真实 Chromium 回归：延迟最终税费、金额不变、税额增加、仅国家响应、错误账单、其他订单、税费接口失败、响应乱序、到期未稳定，以及两个 IP 检查窗口内金额变化。所有测试流量由本地 fixture 拦截；测试通过不代表真实扣款成功。
