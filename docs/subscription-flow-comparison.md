# 订阅办理：旧流程与新流程

后台“支付全监控 → 订阅流程配置”或“代理管理 → 付款配置”提供两个独立选择，默认 **新提链＋旧付款及后续**：

| 结账链接生成流程 | 付款及后续流程 | 执行方式 |
| --- | --- | --- |
| 旧 | 旧 | generator.py 方式提链 → 协议付款 → 旧版生效核实及续费处理 |
| 旧 | 新 | generator.py 方式提链 → 新版接收同一结账单付款 → 新版生效核实及续费处理 |
| 新 | 旧（默认） | cs-live CreateCheckout 提链 → 协议付款 → 旧版生效核实及续费处理 |
| 新 | 新 | cs-live 提链 → cs-live 付款、生效核实及续费处理 |

第一段负责从申请准备到生成结账链接，订阅办理和独立结账链接页面共用 `payment.checkout_flow`。第二段从已有结账单开始，付款、生效核实、Session 刷新和续费处理整体由 `payment.subscription_flow` 选择；独立提链不执行第二段。新旧两段自由组合，禁止在交接时重新创建 Checkout。

四种组合共用 `payment.checkout_types` 的套餐长短链设置。长链与短链按本单选择执行，不在交接时转换。Pro 5x/20x 的安装默认值为长链，Team 标准/高级默认短链，Plus/Go 预设短链（尚未上架）；已保存的套餐规则保留。首次升级到拆分配置时按用户要求设为新提链＋旧付款，后续启动保留管理员保存的组合。

新提链刷新后的最小 Session 会加密交给旧浏览器与旧版付款后任务，不使用受理时的旧 AT/Cookie。旧提链接新付款时只传递原 Checkout ID、真实链接及必要初始化字段，新版跳过提链前刷新、账号预查和创建，从原结账单进入付款准备。使用新提链或新付款需要完整 Session；旧提链仍要求当前 AT 有效，旧付款使用短链时需要真实会话 Cookie。

整笔订阅从提链、付款到生效查询、刷新、取消续费和复查共用原订单代理会话。交接不换代理、不重抽账单，不校验实际出口IP；过期或缺失即停。独立续费管理仍使用其全局代理。新申请在受理时锁定两段及套餐类型，已有订单不重写、不重放。

旧版付款与付款后处理来自本地 `before-subscription-rewrite-20261028-203008/source-and-config.zip`，基线提交 `7e1dfd40ec01463a0265985f1b54c90daaa18487`。本次按用户另行提供的 `generator.py` 更新旧提链：系统 curl；long 使用 iOS/Hosted 及真实长链或 Stripe init，short 使用 Web/Custom 及官方短路由。继续使用后台固定代理，不复制脚本写死的代理、直连对照、自动改地区或拼接缺失 URL。两入口的旧提链均按脚本在探测出口后直接创建 Checkout，不额外刷新或在线预查；旧订阅的浏览器付款和付款后续费顺序保留。失败不自动切到另一套。

## 独立结账链接

| 环节 | 旧流程 | 新流程 |
| --- | --- | --- |
| Session | 有效 accessToken，可仅 AT | 完整 Session，需 sessionToken / 受支持 Cookie；提链前刷新 |
| 前置检查 | 探测后台固定代理的地区和 IP | 原包首页、刷新、账号与当前订阅检查，每个请求检查原代理租约，不探测IP |
| 生成 | 系统 curl，按管理员选择执行 long/short；long 必要时 Stripe init | `CreateCheckout(CheckoutType: 本单已保存的套餐类型, WithPrice: false)`；历史 auto 记录仍省略类型 |
| 返回 | long 返回真实 Hosted 长链并规范为 pay.openai.com；short 返回官方 chatgpt.com/checkout 路由 | 按本单选择提供真实 Hosted 长链或官方短链，不根据上游模式切换 |
| 异常 | 所选 long 无真实长链、所选 short 标识无效或返回异单链接时不报成功；未知不重建 | 同左；升级分支无普通 Checkout 时停止，不进行订阅升级 |

两套均不填写卡片、不选账单、不冻结资金、不付款、不取消续费。请求只允许提链所需操作；新流程不挂付款检查点、不调用 Pay/Recover。`payment.checkout_types` 为两套流程共用的逐套餐 hosted/oaics 规则；受理时保存本单类型，旧全局 checkout_type 不参与选择；`scheduler.link_mode` 仅兼容历史配置，不参与执行；已保存的历史链接仍可查看。下表分别描述两套组件；第 3～5 步按提链选择执行，第 6～13 步按付款及后续选择执行。

| 顺序 / 环节 | 旧流程：generator 提链＋备份浏览器核心 | 新流程：当前 cs-live 接入 |
| --- | --- | --- |
| 1. 提交、排队 | 校验 Session、卡片、套餐与地区；幂等受理、同账号互斥、冻结服务费，排队获取资源 | 同一套平台受理、资金和队列规则 |
| 2. 账单和代理 | 后台正式资料随机选一份并保存加密快照；绑定订单代理，后续复用 | 同一套正式账单池和订单代理规则 |
| 3. 提链前授权 | 使用有效 accessToken，不提前刷新；短链浏览器付款额外要求真实会话 Cookie，长链接受 AT-only | 要求 sessionToken / 有效会话 Cookie；提链前刷新，支持有效刷新凭据接续过期 AT |
| 4. 开头查账号 / 套餐 | 按脚本直接提链；本地检查 Session 元数据和有效期，不额外在线预查，无直接升级实现 | 在线核对账号及当前订阅基线；显式长短链订单遇已有订阅停止，不使用直接升级绕过选择 |
| 5. 生成结账链接 | 按本单选择执行脚本 long/short 分支，不根据上游自动切类型；缺真实长链转待核实 | 按本单套餐配置创建 Checkout 并执行 Hosted 长链或 Custom 短链；不按上游模式切换或拦截，不直接升级绕过选择 |
| 6. 填卡、账单、税费 | 服务器私有 Chromium 打开官方长链或已登录短链页面，填卡及本单账单，等待官方页面返回最终税费和报价 | 按本单所选分支读取税费与报价，通过授权后建立付款方式或确认令牌 |
| 7. 提交付款 | 核对报价/币种和原代理有效期，服务器自动确认，点击官方页面按钮；按原 Checkout/PI 绑定依次允许单次确认及必要批准，阻止重复扣款，不校验出口 IP 一致性 | 使用本单所选 Hosted/Custom 路径，关键请求前保存加密检查点；未知结果不重新确认付款 |
| 8. 付款结果 / 额外验证 | 读取原结账响应中的权威付款证据；明确拒付失败，待验证/未知暂停，旧核实入口只查原单 | 原包区分扣款、授权、处理中、拒付及待验证；待验证自动接续官方 SDK，再 Recover 核实原交易；官方实际要求的交互不能伪造 |
| 9. 核实订阅生效 | **已有**：付款成功后查有效订阅并匹配所购套餐；默认间隔 5 秒、最多 12 次，可配置。查询 401 且有刷新凭据时刷新重查 | **已有**：核对有效订阅和套餐，按原包最多 5 次、间隔 2 秒；401 刷新重查 |
| 10. 取消前刷新 Session | **已有**：生效确认后进入取消阶段，再主动刷新并重新查询；AT-only 旧输入无法刷新，只能沿用有效 AT | **已有**：生效确认后再次主动刷新，然后查询续费状态 |
| 11. 取消自动续费 | 已关闭直接完成；否则持久标记后最多提交一次取消，再查询 `will_renew=false`。结果未知只复查；默认 30 秒、最多 10 次，可配置 | 已关闭直接完成；否则按原包取消并有限复查。原包在特定瞬时失败且查询仍开启时允许第二次取消提交 |
| 12. 保留续费 / 完成 | 选择保留时仍核实生效，但不执行取消；付款、生效、续费结果分别记录 | 相同结果要求，由原包后续处理实现 |
| 13. 恢复与重启 | 使用原结账、原代理查付款；付款后独立持久任务核实生效/续费，不恢复卡号、CVV或重复付款 | 使用原加密检查点 Recover 核实原付款及生效/续费；必要时接续原单批准及 SDK，不重新提链或再次确认付款 |
| 14. 网络异常 | 原代理到期或缺失即停止；不探测、比较出口IP，付款前也不自动换会话/重建 | 会话到期或缺失即停止，不自动换会话；全链条检查租约，不探测、比较出口IP |
| 15. 监控与客户显示 | 管理员可看本单“旧流程”、账单快照、链接及脱敏阶段；客户固定七步 | 管理员可看本单“新流程”，另有协议与 SDK 诊断；客户同样固定七步 |

客户七步保持：**提交申请 → 排队准备 → 办理准备 → 订阅付款 → 订阅生效 → 取消自动续费 → 办理完成**。两套核心调用均在服务器执行；客户不接收后台选择、上游核心请求、检查点、平台代理凭据或实际账单快照。

## 旧订阅流程可补充的事项

1. **已有套餐处理**：旧脚本提链不额外检查已有订阅，也不实现直接升级；当前显式长短链选择不走直接升级；历史 auto 检查点保留原恢复规则。独立提链菜单始终不执行升级付款。
2. **统一要求可刷新的完整 Session**：旧版已有生效检查和取消前刷新，但仍兼容 AT-only。若要求每单都必须刷新后取消，应在受理时要求刷新凭据，避免付款后才发现无法刷新。
3. **额外验证接续**：旧版遇到待验证会暂停，不能称旧版已具有新流程的 SDK 自动接续能力。需要时应按原交易实现受支持的接续入口，不再次付款。
4. **参考一致性边界**：保留固定代理、正式账单、幂等/权限与同单结果验证。不复制脚本敏感日志或缺链时拼造 URL，也不能将脚本的 payable=false 当付款成功。旧浏览器短链需要真实 Cookie；这是网页登录所需，不伪造 AT-only 登录态。

生效核实和取消前刷新已经存在，不需要重复增加一套。是否成功始终以真实付款、套餐生效及续费查询结果为准，不能用页面跳转、按钮点击或 SDK 回调替代。

## 持久化与权限

`payment.checkout_flow` 和 `payment.subscription_flow` 为两个独立管理员配置。受理事务在同一付款配置行上加共享锁，将提链选择保存为 `checkout_runs.flow`，付款及后续选择决定是否创建 `subscription_protocol`。历史订阅仍按协议记录识别，历史独立提链补 `legacy`，不重放任务。执行、核实与重启均读取原单记录。旧管理页面未传新字段时保留已有值。非法值拒绝受理，普通客户不能改配置，客户详情/API 不输出此内部标识；管理员详情同时显示本单两段实际流程。付款关闭时仍允许独立提链。
