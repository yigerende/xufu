# cs-live 订阅流程接入

后台按两个独立设置组合提链与付款，默认新提链＋旧付款及后续。`payment.checkout_flow` 选择从准备到生成链接的旧脚本或新版；`payment.subscription_flow` 选择付款、生效核实、刷新与续费处理的旧浏览器方案或 cs-live 方案。独立结账链接页面只读取提链选择。四种组合共用后台逐套餐长短链配置，完整对比见 [新旧流程对照](subscription-flow-comparison.md)。

旧提链接新付款通过私有 `PayOptions.PreparedCheckout` 交接原结账标识、链接及初始化字段；校验同单身份后跳过新版提链前流程，直接在原结账单准备付款。新提链接旧付款调用 `CreateCheckout`，返回的刷新后 Session 仅在服务端加密交接，不进入 JSON 或日志。旧付款仍使用官方页面浏览器，并继续旧版生效核实、取消前刷新和最多一次取消策略。所有组合保持一单一代理会话、同一出口 IP、同一随机账单快照；交接不重新创建结账单。下文描述新版组件。

## cs-live-source 完整流程

用户最新要求将套餐配置作为执行规则：payment.checkout_types 中 hosted 固定执行长链，oaics 固定执行短链，供新旧流程及两个入口共用。新单受理保存套餐对应类型，传入 Pay/CreateCheckout；显式选型不读取上游 checkout_ui_mode 来分流或报模式不匹配，也不经过直接升级绕过所选路径。默认 Pro 5x/20x 长链、Team 标准/高级短链，Plus/Go 仅预设短链尚未上架。历史 auto 保留原包默认分流；已提交付款继续按原检查点恢复，不重建或重付。真实链接、结账身份、金额和付款结果校验保留。

1. 校验 Session、银行卡、账单、地区、套餐、代理，建立交易上下文和可恢复检查点。付款需要 accessToken 与 sessionToken。
2. 首页 → 提链前刷新 Session → 核对账号 → 当前订阅基线。源码在刷新返回 session_expired 且原 AT 存在时允许继续在线核对原 AT，其他刷新错误停止；账号查询 401 时刷新重查。
3. 无冲突订阅时初始化支付上下文并创建一次 Checkout。显式长短链订单遇已有有效订阅停止，不用 Plus → Pro 5X 直接升级绕过选择；历史自动模式及其已提交升级检查点保留原逻辑。
4. 按本单配置选择 Hosted/Custom 付款分支，上游模式字段不能改变该选择。Hosted 读取真实长链接、初始化付款页并更新账单税费；Custom 读取税费及原结账上下文。得到实时金额/币种后调用授权回调。
5. 创建付款方式或确认令牌，在不可安全重放的请求前同步保存检查点，提交付款并查询原交易。区分已扣款、未扣款、待处理、仅授权、需要额外验证；必要的原结账批准属于原交易。
6. 已扣款先保存资金结果，再核实订阅生效及套餐。最多查询 5 次、间隔 2 秒；遇 401 刷新后重查。失败不能抹掉已付款。
7. 保留续费则完成；默认取消时再次主动刷新、查询续费状态，已关闭直接完成，否则提交取消并最多查询 5 次、间隔 2 秒确认关闭。附件在特定瞬时失败且查询仍开启时允许第二次取消提交。
8. Recover 校验原检查点、查询原付款并继续生效/续费核实，不重新建单或再次确认付款；Custom 原交易可能继续待批准动作。requires_action 可接续原包官方 SDK：retrievePaymentIntent → 核对原 ID/状态 → handleNextAction → Recover。SDK 可直接完成，也可能要求持卡人交互；只以服务端原交易核实结果判定付款。

## xufu 完整流程

| 客户固定步骤 | 服务端行为 |
| --- | --- |
| 提交申请 | 校验账号、方案、地区、完整 Session、卡片；幂等受理及同账号互斥；后台正式账单池均匀随机抽一份，保存加密副本，冻结服务费。 |
| 排队准备 | 原持久队列与容量限制；卡片只在内存等待，无对应地区代理则排队，重启不会恢复卡片或重付。 |
| 办理准备 | 绑定订单代理会话及出口，刷新授权、核对账号，按本单套餐类型创建一次 Checkout。显式选型的已有 Plus 账户按订阅冲突处理，不直接升级；独立提链不升级。 |
| 订阅付款 | 按本单选择进入 Hosted 长链或 Custom 短链，不根据上游模式切换。待验证时同一任务自动运行官方 SDK 页面，完成后 Recover 核实原交易，继续后续步骤。同步加密检查点与提交标记，权威付款结果和服务费幂等结算。 |
| 订阅生效 | 附件查询与刷新时序；付款与生效状态分别保存。 |
| 取消自动续费 | 默认刷新、查询、提交、复查；保留时固定标题不变，下方显示“已选择保留”。 |
| 办理完成 | 生效及所选续费设置都确认才完成；后续异常保留付款成功，提示待核实。 |

## 保留规则与适配差异

- 每单一个代理会话：提链、付款、恢复、生效、刷新、取消、复查均通过原订单私有 CONNECT 桥及同一代理会话。每次 HTTP 尝试前检查执行/容量租约、资源启停与有效期；按2026-10-30要求不探测或比较出口IP。新流程不换会话重新提链，不直连兜底。独立续费工具仍用全局代理。
- 每单一份随机正式账单：只选 enabled=true、test_only=false 且字段完整的后台资料；后续编辑、删除和恢复不重新抽取，不编造地址或按税率选地区。
- 保留 xufu 账号、余额、冻结、账本、队列与权限。未知付款保留冻结，仅恢复原交易；明确未付款解冻，已扣款只结算一次。Custom/升级检查点继续按原包恢复，可补录原实收；Custom 必要时接续原交易批准及 SDK，不重新创建 Checkout 或再次确认扣款。已确认扣款后继续生效及所选续费处理。
- 新订阅取消策略遵循原包：瞬时失败后先查询，仍开启才进行原包限定的重试；不再叠加“一律只发一次”的拦截。旧订阅与独立续费工具保留既有规则。付款确认仍不可重放。
- 套餐映射 pro→pro20x、team_premium→team5x，其余支持套餐直接映射。普通/高级席位分别传入，团队名称按原包固定为 Team。平台新单 Pay/CreateCheckout 传入受理时保存的套餐类型；Pay 与 CreateCheckout 均按所选类型执行，检查点保存实际选定分支供原交易恢复。历史 auto 记录省略类型，历史 hosted/oaics 保留原参数。SDK 的空模式与 Quote 保持原包默认 Custom。独立 Hosted 提链只返回同单真实长链，Custom 提链固定返回同单官方短路由，即使上游带有 Hosted URL 也不替换短链。
- 新提链或新付款必须有刷新凭据，受支持分段 Cookie 可组装为 sessionToken；仅在选择新提链时，AT 过期但刷新凭据期限有效可进入服务端刷新；旧提链仍要求有效 AT。最小授权与检查点加密保留最长 24 小时；完整成功或明确失败清理，待核实保留至到期。PAN/CVV 不进入检查点/数据库。
- 新增 subscription_protocol 表，不把旧单伪装成新协议。新订阅在 Go 内运行，最低 Go 1.25；旧单保留 Chromium 兼容。普通协议付款不依赖 Node/Chrome；需要官方 SDK 接续时使用镜像内的 Playwright/Chromium。
- 同步保存实际返回链接供管理员排查；未取得的链接不拼造。适配不增加创建 Checkout 次数。

## 账单字段映射

附件 Billing 所需资料由现有后台字段完整提供，无需新增后台字段：

| 附件字段 | xufu 来源 |
| --- | --- |
| Name | 正式账单 first_name + last_name |
| Line1 / City / State / PostalCode | 抽中账单的街道、城市、州、邮编 |
| Country | 现有 US 账单池固定 US，与订阅地区独立 |
| Email | 本次订阅账号邮箱，不使用账单条目的历史邮箱 |

附件当前不要求电话号码或地址第二行。后台校验比附件更严格：美国州代码、5 位或 ZIP+4 邮编、姓名/城市/街道完整；无合格资料不受理、不冻结或提链。字段齐全不代表真实支付一定通过。

## 客户隐私与后台监控

客户浏览器只提交本站业务请求和轮询业务状态，不执行上游核心调用。客户网页及 API key 接口不返回订阅结账链接、检查点、核心地址、报文、平台代理凭据、刷新令牌或完整账单。本人输入的 Session 和卡片仍会出现在本人提交请求中，不能对此隐藏。

支付全监控记录受理、排队、费用、网络、刷新、账号、提链、税费、付款、生效、续费、最终结果，以及可用的 HTTP 状态、请求关联编号、尝试次数、网络阶段耗时和白名单诊断码。实际结账链接加密进入管理员历史，页面不自动访问链接。原始报文、任意错误文本、PAN/CVV 和授权凭据不进入监控输出。

常规 HTTP 诊断有界异步落库，溢出/保存失败有汇总日志；关键资金及终态记录与业务事务一致。历史订单不伪造新记录。

## 2026-10-29 官方 SDK 验证接续

Pay 返回待验证后，同一订单任务自动运行原包官方 SDK 页面并触发其初始“继续验证”按钮，随后 Recover 核实原交易并继续生效和续费处理；无需客户或管理员点击后台入口。恢复原单时也按 Recover → 待验证则 SDK → Recover 接续，每次任务只执行一轮 SDK，不循环重试挑战。自动模式不开放交互会话、不截图。原包 CLI 的 TLS 入口与手动打开页面由服务端自动运行承接；页面和官方 SDK 调用顺序保持原样，这不是声称原包 CLI 本身没有人工入口。

每次 Pay/Recover 保留原包单请求45秒、单次操作240秒的默认预算；外层任务另留10分钟SDK与后续恢复时间并持续续租，不能把SDK时间算进付款本身的240秒。支付全监控记录自动验证启动、SDK诊断结果、超时/中断和原交易复查。管理员原有“继续原付款验证”仅作为已暂停订单的异常处理入口，不再是正常流程的必经步骤；该入口仍只有发起管理员可以交互。客户不接收 SDK 上下文、交易密钥、核心报文或验证地址。

每个外部请求（包括复用 HTTPS 连接的请求）先经私有管道检查原代理租约与期限；连接限定公网 HTTPS。最多 10 分钟且不能超出原代理有效期。关闭、进程重启、到期停止接续并保留原交易待核实，不更换代理、重建结账或重付。官方 SDK 能自行完成的验证自动完成；上游实际要求持卡人交互时，不能伪造交互或把超时当成功。旧的已暂停订单保留原状态，上线不会批量重放。

SDK 回调只记录有限的 outcome/code，随后运行原 Recover 读取真实付款状态并继续生效与续费。浏览器报告完成不直接扣服务费或标记成功。截图和输入不落库、不写文件或日志。后台补充付款原始状态、next_action/SDK 类型及相关资源是否存在，不保存 stripe_js URL 或挑战内容。

与原包按 Go AST 逐函数比对：2026-10-30复核453个函数相同、6个函数有长短链选择/混合交接/链接留存及检查监控适配（详见subscription-diagnosis-20261030.md）；已恢复原包固定团队名。原始页面和脚本逐字一致（忽略文件末尾换行），SHA-256 分别为 `6f63e9b14b2d0829e85c8c59cde2617995badcec1b111cdfe38e8aafe0de655e`、`a7c39adae40e4ad8585b64a20fb2ba6806967f5d409adefcb7e152178d8184bc`。原包 CLI 的终端/文件交接由本站队列、加密数据库和管理员窗口承接，业务付款分支保持原包逻辑。

## 支付全监控人工关闭

管理员可对服务费仍冻结、付款未确认成功的订单选择“人工关闭订单并释放服务费”，填写原因并确认。订单锁、资金释放、停止队列/租约、原状态快照和审计同事务提交，再关闭内存任务与验证窗口。重复点击不会重复释放，旧 worker 的迟到回调不能覆盖关闭或重新收费。

这是本站办理终止，不是银行撤销或退款：submitted 标记、原加密检查点、账单、代理及已有诊断继续保留，管理员可见关闭前付款状态和原因。已向上游提交的交易仍可能扣款，关闭后不自动核实、生效或取消续费，需要运营另行核实。已结算服务费/付款成功的订单不通过此入口退款；客户无此权限。
